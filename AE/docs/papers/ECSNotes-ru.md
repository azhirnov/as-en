
# Проблемы ECS

## Неполная совместимость с SIMD

Для SSE/Neon использование `float3` типа это потеря 1/4 производительности, а более широкие SIMD, типа AVX, уже не применить.
Более оптимальное решение это разложить float3 тип на массив скаляров: `x[], y[], z[]` тогда AVX полностью используется.
Но такая раскладка потребует в 3 раза больше компонентов: PositionX, PositionY, PositionZ вместо Position.
А перемещение компонентов обойдется в 3 раза дороже из-за большего количества кэш промахов.

**Решение: Отказаться от перемещение компонентов.**

Если не требуется перемещать компоненты, то становится проще поменять раскладку под SIMD.
Редкое удаление сущности решается через смещение данных влево, как у вектора (std::vector).

## Нет компонентов произвольного размера

Бывает нужно сделать небольшой массив в компоненте, укозатель ломает принцип DOD, статичный массив оставляет пустое место.
В идеале сделать компоненты переменного размера, но это сломает доступ по индексу и усложнит логику перемещение компонентов.

**Решение: Необязательный доступ по индексу.**

Для компонентов с произвольным размером можно смещать указатель при итерировании, вместо индексации.
Вместе с неперемещаемыми компонентами это сильно упростит работу с такими компонентами.


## Хранение иерархии

Принцип DOD требует хранить данные линейно, что плохо сочетается с графами.

**Решение: Иерархия хранится отдельно.**

Система для ускорения работы может хранить иерархию компонентов в любом виде.
И это вписывается в принципы ECS.
Добавление и удаление компонентов и сущностей отслеживается через сообщения.


## Тяжело перейти с ООП

В отладчике удобно просматривать объект целиком, а не отдельные компоеннты раскиданные по разным хранилищам.

**Решение: Не требуется полность отказываться от ООП.**

ООП представление может остаться как ссылка на объект в компоненте ECS. Тогда в ООП классе можно хранить данные к которым редко обращаются, либо копировать данные с частым обращением в компоненты.


# Оптимизация

## Память

ECS предполагает последовательное выполнение систем для блоков памяти.
Таким образом получаем максимальную скорость чтения из RAM, но можно сделать лучше - выполнение систем для блока в кэше, тогда скорость доступа к памяти будет равна скорости L2/L3 кэша.
Это аналогично тайловой архитектуре на GPU. Работает до тех пор, пока не появится точка синхронизации - необходимость прочитать за пределами кэша.

Тут важно знать размер кэша, чтобы данные не вытеснялись из L2 кэша.
